1. MVP OBJECTIVE

Build a working vertical slice of an AI Deployment Decision Engine that helps
an organization determine whether a proposed AI initiative is worth deploying.
The MVP demonstrates the complete path from an ambiguous business problem to
an evidence-backed, economically reasoned assessment.

The goal is NOT a complete enterprise AI economics platform. The goal is to
demonstrate the core product thesis and the engineering decisions behind it.

2. CORE PRODUCT THESIS

This is NOT an AI ROI calculator. It is an AI-assisted deployment decision
system.

Core question:
"Should we deploy AI here, and if so, what is the economically and
operationally sensible way to do it?"

The system must be willing to steer AWAY from AI when warranted.

Core principle: AI capability != AI suitability. A technically solvable
problem is not necessarily an economically worthwhile AI problem. The system
can decline to prescribe an answer at all, surfacing instead the facts a human
needs to apply their own judgment.

3. CORE PRODUCT FLOW

Business problem
-> AI interviewer (adaptive, state-driven)          [10]
-> Structured assessment state                      [5]
-> Identify missing inputs
-> Sector benchmark cross-reference                 [4]
-> AI solution estimation                           [7]
-> Deterministic economic engine                    [8]
-> Scenario / sensitivity analysis                  [8.10]
-> Ranked Decision Drivers (not a forced category)  [9.5]
-> Cited decision report                            [13]

The final output is a ranked list of Decision Drivers plus an explicit
uncertainty callout. The system does NOT output a category (BUILD / PILOT /
DON'T BUILD) and does NOT prescribe a verdict. This is stated once here and
enforced in 9.8; it is the single most load-bearing product decision.

4. LOCKED SECTORS

STATUS: implemented — data/sector_benchmarks/*.json, loaded by lib/benchmarks.py

Two sectors, chosen for cross-verifiable public benchmark data and for being
structurally different processes (real-time conversational vs. batch document
processing) so the economic engine has to genuinely flex.

4.1 Customer Support Automation
Intended sources: Zendesk CX Trends, Gartner/HDI cost-per-ticket benchmarks,
Glassdoor/Levels.fyi salary data (India + US), model-provider API pricing.
Ground-truth figures wanted: cost per ticket, average handling time, tickets
per agent per day, fully loaded agent salary, automation adoption rate.

4.2 Document / Invoice Processing (Accounts Payable / back-office)
Intended sources: Ardent Partners AP benchmark reports, Levvel Research AP
surveys, Deloitte/IDC automation cost studies, published IDP/OCR vendor
pricing (Rossum, Nanonets, AWS Textract).
Ground-truth figures wanted: cost per invoice handled manually,
straight-through-processing rate, fully loaded AP clerk salary, OCR/IDP
per-document pricing.

4.3 Pack format
Each sector ships as a static JSON pack. No live search or API calls at
runtime. Every figure carries:

  value (or min/max), unit, provenance, verification, source, source_url,
  as_of, geography, notes

`provenance` uses the section 6 tags (in practice `sourced` or `assumed`).
`verification` is a SEPARATE quality axis recording how firmly the figure was
checked:

  primary_document  the source document/page was retrieved and read
  search_snippet    attributed to a named primary source, but read from a
                    search result because the source blocks retrieval
  unverified        no primary source located

GUARDRAIL: a figure may only claim `sourced` if it names a retrievable source
with a URL and a date. `sourced` + `unverified` is rejected by the loader.
Anything whose chain of custody stops at a secondary summary must be tagged
`assumed`. This exists so an industry average can never be laundered into
something that reads as independently sourced.

4.4 The two packs are not equally solid, and that is recorded, not smoothed
  document_processing  11 figures, 9 sourced, 8 read from the primary document
  customer_support      8 figures, 2 sourced, 0 read from the primary

Document processing is genuinely grounded (Ardent Partners AP Metrics 2025;
AWS Textract list pricing). Customer support is not: the named primary
sources are gated, and the widely-quoted cost-per-ticket figures trace only to
aggregator summaries, so they are tagged `assumed`. Treat customer-support
economics as materially weaker than document-processing economics until the
primaries are obtained.

Sector selection is the first interview input (single select), keeping the
interview grounded in real data.

5. STRUCTURED ASSESSMENT STATE

STATUS: implemented — schemas/assessment_state.py

Single source-of-truth Pydantic model, shared by every module (ARCHITECTURE
3.8). No module redefines these shapes. Current fields:

  Identity
    sector            customer_support | document_processing
    problem           str
    geography         str | None    controls labor-rate and currency resolution;
                                    never defaulted (an unknown geography must
                                    not silently inherit US rates)
    currency          derived property from geography — never collected

  Economic inputs (labor baseline, 8.1)
    process                     str | None
    monthly_volume              RangeEstimate
    avg_time_per_unit_minutes   RangeEstimate
    current_headcount           RangeEstimate
    worker_role                 str          the user's own words
    worker_role_canonical       ProcessRole | None   labor-registry lookup key
    fully_loaded_annual_cost    RangeEstimate   (benchmark-substitutable)
    fraction_time_on_process    RangeEstimate 0-1  (benchmark-substitutable)

  Other current-cost components (8.2)
    annual_tooling_cost              RangeEstimate | None
    monthly_tooling_cost             RangeEstimate | None
    error_rate                       RangeEstimate | None   fraction 0-1
    rework_time_per_error_minutes    RangeEstimate | None
    annual_rework_cost               RangeEstimate | None
    annual_other_direct_cost         RangeEstimate | None
    other_direct_cost_description    str | None

  All optional by design: the user is never pushed to invent a number, and an
  uncollected component stays ABSENT rather than becoming zero (8.2).

  Current-process quality (8.6)
    current_quality_metric   CurrentQualityMetric | None
    current_quality_value    RangeEstimate | None

  The metric NAME travels with the value, so nothing downstream can silently
  read an exception rate as an accuracy rate. Without both, the current-vs-AI
  quality comparison stays ABSENT rather than assuming today's process is
  perfect.

  Feasibility inputs (9.2)
    required_accuracy      RangeEstimate 0-1
    existing_data          str            free-text description
    data_readiness         none|minimal|partial|good|excellent   (scored)
    current_tools          str[]
    integration_complexity small|medium|large

  Risk inputs (9.3), under `risk`
    failure_impact            str            free-text description
    failure_impact_severity   negligible|minor|moderate|major|severe (scored)
    compliance_exposure       str[]          canonical registry keys
    compliance_requirements   [{ standard, stated_as, hard_requirement }]

  Two risk quantities are deliberately NOT collected. `failure_probability` is
  DERIVED in calc/risk_score.py from the selected architecture's own error
  metrics — asking the user to guess at something the system can compute would
  waste a question and compete with an observable fact. `reliability_gap` is
  likewise derived, from required minus achievable accuracy.

  Implementation (8.5)
    process_stages   [{ stage, required, buy_or_build, vendor_or_approach }]

  Bookkeeping
    provenance        field -> provenance tag
    field_resolution  field -> { status, attempts, reason }
    turn_count, complete, status

The state carries NO solution field. `SolutionEstimate` (7) is a separate
object produced by the estimator and passed alongside the state; it is never
written back into it. Every consumer — economic engine, scoring, drivers,
alternatives, report — takes both as separate arguments. An earlier draft of
this section listed an `ai_solution` field; it was never built, and adding one
would create a second place for the solution to live.

Note the deliberate pairing of a free-text field with a scored CATEGORY
(`existing_data`/`data_readiness`, `failure_impact`/`failure_impact_severity`).
Free text cannot deterministically produce a sub-score, so the LLM classifies
into a category and code maps the category to a number — the same division of
labour as the effort bands in 7.4. The description is kept for the report.

RangeEstimate — the canonical ranged value — is { min, max, confidence,
provenance, source, source_id }. It is defined ONCE, here, and used by the
interviewer, the estimator, the benchmark loader and every calc module.
`source` is the rendered citation (presentation only); `source_id` is the
stable evidence key that provenance validation and the report's evidence index
match on, so reformatting a citation cannot invalidate a real evidence link.

A user-supplied single number is stored as a point range (min == max), not as
a scalar and not as a fabricated spread. Collapsing a range to one number is
an explicit call to `point()` at the site that needs it, never a silent
transformation at collection time.

6. DATA PROVENANCE

STATUS: implemented — Provenance enum in schemas/assessment_state.py

Five-value tag set, preserved end-to-end from interview to final report. No
number appears without a traceable origin.

  user_provided  stated directly by the user in the interview
  sourced        pulled from the sector benchmark pack
  estimated      LLM-generated estimate, always a range
  assumed        a default applied because nothing else was available, always
                 flagged as an assumption in review/report
  derived        calculated from other fields (arithmetic, not a guess)

THIS IS THE ONLY PROVENANCE VOCABULARY IN THE SYSTEM. Earlier drafts of
sections 8 and 9 used a parallel set; it maps in as:

  benchmark, evidence -> sourced    (specific origin recorded in the citation)
  llm_estimate        -> estimated
  assumption          -> assumed

Never silently substitute a benchmark value. If the user has not provided a
value the pack covers, surface it explicitly: "We don't have your actual [X].
Industry benchmark is [value] ([source]). Use this, or provide your own?"
Provenance becomes `sourced` if the user accepts, `user_provided` if they
override.

Known gap: benchmark-substitutable fields are currently filled from the pack
without that prompt, because the review screen (14, SCREEN 3) where the choice
would be presented is not built.

7. AI SOLUTION & ARCHITECTURE ESTIMATOR

STATUS: implemented — solution/*.py; weaknesses tracked in docs/estimator_todo.md

The estimator does not freely invent an architecture. It decomposes the
assessed workflow into required capabilities, then matches those capabilities
against a curated Solution Registry of established patterns and implementation
options (custom code, n8n, Make, Zapier, managed AI services, LLM/RAG, voice
providers).

7.1 Division of responsibility
- LLM proposes and explains: decomposes the workflow into capabilities,
  estimates per-task automation, explains fit. It never selects a pattern.
- Solution Registry constrains the solution space: patterns ->
  implementation options -> providers, each with explicit Compatibility
  metadata (capabilities, scale, latency, deployment, compliance, complexity).
- Reference solution provides the sector baseline, plus the conditions under
  which departing from it is legitimate.
- Deterministic logic filters, ranks and calculates.

7.2 Estimator outputs
- recommended solution pattern / architecture
- candidate implementation options
- task-level and overall automation-rate range
- relevant performance/accuracy range
- integration-complexity band
- engineering-effort band and hours
- human-in-the-loop requirements per task
- technical risks and mitigations
- key technical uncertainties
- reference comparison (7.6)
- confidence for each estimate

7.3 Ranges and bands, never false precision
LLM estimates stay ranges/bands and are always displayed as a range plus a
confidence label ("60-75%, medium confidence"). Never present an LLM-generated
estimate as a precise value.

7.4 Engineering effort bands
Effort uses predefined bands mapped to hours in code:

  small  24-60 hrs      medium  80-200 hrs      large  200-500 hrs

Hours and the fully-loaded engineering rate are kept SEPARATE, each with its
own provenance, and cost is derived from the two. All three are currently
tagged `assumed` — they are explicit assumptions, not sourced figures.

7.5 Core principle
The LLM proposes and explains; the Registry constrains the solution space;
deterministic code filters, ranks and calculates. Any change that lets the LLM
pick a pattern ID directly is a regression.

7.6 Ranking (deterministic)
Candidates are filtered to those whose chosen implementation covers every
required capability, then scored on four weighted terms, each normalised 0-1
(maximum 10.0):

  reference_alignment  x 4.0   follows the sector baseline — or deviates for a
                               reason the baseline itself sanctions
  scale_fit            x 2.0   the chosen stack is rated for the volume
  compliance_fit       x 2.0   the stack covers the stated constraints
  complexity_pref      x 2.0   prefer the cheapest build that still fits

Sector influence enters ONLY through the reference solution — never as a bare
"this is the sector's pattern" bonus. Scoring uses the one implementation
actually chosen, not every implementation the pattern lists, so a pattern
cannot score higher for merely offering more options. Implementation selection
prefers a scale-appropriate build before a low-complexity one, so effort is
not understated by choosing a tool that cannot carry the volume.

7.7 Deviation conditions
Each reference solution carries machine-evaluable conditions under which
leaving the baseline is legitimate (e.g. monthly volume above a threshold
releases the design to a custom or managed-service implementation). Conditions
that depend on facts the assessment does not capture are typed MANUAL and are
surfaced as uncertainties rather than silently failing to fire.

Alignment ordering matters and is deliberate: a fired condition licenses a
different BUILD, not a different ARCHITECTURE. The baseline pattern adapting
its implementation therefore outranks a foreign pattern that merely happens to
use a sanctioned implementation kind.

7.8 Reference comparison
The estimator reports the reference id, expected vs selected pattern, whether
they match, the SAME alignment value the ranker used, the conditions that
fired, and the conditions that could not be evaluated. Reporting the ranker's
own number prevents the report from asserting a rationale the ranking did not
actually apply.

8. ECONOMIC ENGINE

STATUS: implemented — calc/{models,labor,current_state,ai_state,implementation,
lifecycle,benchmark_check,sensitivity,engine}.py; validated by
scripts/economic_cases.py; weaknesses tracked in docs/economic_engine_todo.md

The Economic Engine converts the current-state assessment and the selected AI
solution into a transparent, auditable economic comparison.

The engine is deterministic: LLM-generated estimates from the AI Solution
Estimator are treated as assumptions/ranges with provenance, while all costs,
savings and financial metrics are calculated in code (calc/). The LLM never
outputs a number that enters these formulas.

The model uses a TASK-LEVEL approach rather than assuming that an overall AI
automation percentage translates directly into equivalent labor or headcount
reduction. This follows the task-based view of automation, where technology
automates some tasks, augments workers on others, and creates or retains human
tasks.

8.1 Current-State Task Economics

Where possible, represent the current process as a set of tasks:

Task
  |- workload share
  |- volume
  |- handling time
  |- labor role
  |- loaded labor rate
  \- current cost

For task i:

  Task Cost_i = Task Volume_i x Handling Time_i x Hourly Labor Rate_i

Alternatively, where workforce-level data is available:

  Attributable Labor Cost =
    Number of Workers x Fully Loaded Annual Cost
    x Fraction of Time Spent on Process

The engine supports both formulations. When both are available they are
treated as INDEPENDENT calculations and used as a consistency check — never
silently combined, and never averaged. A material divergence between the two
is itself a finding and is reported.

8.2 Current Annual Cost

  Current Annual Cost =
    Attributable Labor Cost
    + Existing Tooling / Infrastructure
    + Error / Rework Cost
    + Other Direct Operating Costs

Every input carries provenance (section 6). Unknown values are never silently
fabricated: an absent component is reported as absent, not as zero.

8.3 AI-State Task Economics

The AI scenario is evaluated at the task level. For each task, determine:

  - autonomous work
  - AI-assisted work
  - human-reviewed work
  - human-only work
  - expected residual labor
  - AI-specific operating costs

The model MUST distinguish:

  Automation
    != Productivity Improvement
    != Labor Hours Eliminated
    != Headcount Reduction

AI assistance may increase worker productivity without proportionally reducing
headcount. Brynjolfsson, Li & Raymond, "Generative AI at Work" (NBER Working
Paper 31161, 2023; published Quarterly Journal of Economics 140(2), 2025)
studied 5,179 customer-support agents and found a 14% average increase in
issues resolved per hour (34% for novice/low-skilled workers, minimal effect
for experienced ones). The published QJE version reports 15% rather than 14%;
both figures are recorded here because the difference between a working paper
and its published revision is exactly the kind of detail this system must not
launder away.

That evidence supports an augmentation/productivity SCENARIO. It does not
license an assumption of 14% headcount reduction, and it is not a
company-specific input.

For each task:

  Residual Labor Cost_i = Current Task Labor Cost_i x Residual Work Fraction_i

Human review cost is modeled separately where applicable.

  AI Task Cost_i =
    Residual Labor Cost_i + Human Review Cost_i + AI Operating Cost_i

8.4 AI Annual Operating Cost

  AI Annual Operating Cost =
    Residual Labor
    + AI / API Inference
    + AI Infrastructure
    + Human Review
    + Monitoring
    + Maintenance
    + Other Recurring Costs

The engine must not assume that reduced workload automatically produces
equivalent headcount savings. Where labor capacity is freed but headcount is
retained, the result is represented as a capacity/productivity gain, NOT as
labor-cost elimination. Which of the two applies is an explicit, user-visible
choice — never a silent default.

8.5 Staged Implementation Cost

Implementation is modeled as explicit stages:

  - Data collection / preparation
  - Model selection / prompting / fine-tuning
  - Integration
  - Testing / QA
  - Deployment
  - Monitoring setup
  - Ongoing maintenance

For each stage: Required (yes/no), Approach (buy/build), Cost, Provenance.

  Buy   = vendor / subscription / API / managed-service cost
  Build = Engineering Hours x Loaded Labor Rate

Engineering effort comes from the predefined Small / Medium / Large bands
produced by the AI Solution Estimator (section 7.4). The LLM does not invent
hours or labor costs.

8.6 AI Lifecycle Cost and Unit Economics

The engine accounts for implementation AND recurring operating costs, rather
than evaluating AI only through API/token expenditure.

For the MVP one-year horizon:

  First-Year AI Cost = Implementation Cost + AI Annual Operating Cost

Normalized unit economics, where meaningful:

  Current Unit Cost    = Current Annual Cost / Annual Valid Output
  AI Unit Cost         = AI Annual Operating Cost / Annual Valid AI Output
  First-Year Unit Cost = First-Year AI Cost / Annual Valid AI Output   (optional)

"Valid output" means output that met the required accuracy bar — an AI system
producing more units at a lower per-unit cost has not improved anything if a
larger share of them fail review.

This follows lifecycle-cost approaches such as the proposed Levelized Cost of
Artificial Intelligence (LCOAI) — Curcio, "Introducing LCOAI: A Standardized
Economic Metric for Evaluating AI Deployment Costs" (arXiv:2509.02596, 2025) —
which argues AI economics should account for lifecycle CAPEX/OPEX and normalize
cost against productive output rather than relying on API or compute prices
alone.

Two honest caveats: LCOAI is a recent single-author proposal, not an
established standard; and LCOAI proper discounts costs and volumes to present
value over a multi-year asset life, whereas the MVP uses an undiscounted
one-year horizon. The MVP therefore borrows the NORMALIZATION IDEA (cost per
valid output), and must not describe its output as an LCOAI figure.

8.7 Annual Savings and First-Year Economics

  Estimated Annual Cost Savings = Current Annual Cost - AI Annual Operating Cost

This is COST SAVINGS ONLY. Productivity, revenue, quality, capacity or other
benefits are not silently included unless explicitly modeled.

  First-Year Net Benefit = Estimated Annual Cost Savings - Implementation Cost
  Monthly Net Benefit    = Estimated Annual Cost Savings / 12
  Payback Period         = Implementation Cost / Monthly Net Benefit

Payback is calculated ONLY when monthly net benefit is positive. Otherwise the
engine reports:

  "No positive payback under the current assumptions."

A negative or absent payback is a legitimate result, not an error state.

8.8 Benchmark Cross-Check

Sector benchmarks are a sanity check, never an additive cost.

  Calculated current cost:  X per invoice
  Industry benchmark:       Y-Z per invoice
  Assessment:               within range / below benchmark / above benchmark

Benchmarks are never added to the calculated baseline, because they may
represent the same underlying labor or operating costs (double-counting).

8.9 Evidence and Provenance

Economic inputs carry the five-tag provenance system defined in section 6:

  user_provided | sourced | estimated | assumed | derived

Research evidence informs modeling assumptions and ranges; it is not treated as
a company-specific input unless the context is demonstrably comparable. Evidence
that AI assistance raised support productivity by 14% can support an AI-assisted
productivity scenario; it does not become this company's expected automation or
headcount reduction.

Note on vocabulary: earlier drafts of this section listed benchmark / evidence /
llm_estimate / assumption as separate tags. Those are NOT additional tags — they
map onto section 6's five, which remain canonical and are the only vocabulary in
the code:

  benchmark, evidence -> sourced      (specific origin recorded in the citation)
  llm_estimate        -> estimated
  assumption          -> assumed

8.10 Sensitivity Interface

The Economic Engine exposes the variables required for downstream Decision
Driver analysis (section 9.5), for example:

  automation rate, task workload share, labor rate, handling time,
  AI inference cost, human review rate, implementation hours, AI operating cost

For any variable:

  Baseline
    -> Lower Bound -> Recalculate
    -> Upper Bound -> Recalculate
    -> Measure Economic Impact

The Economic Engine does NOT decide which variable matters most. It provides
deterministic recalculation; the Decision Driver module ranks variables by
impact.

8.11 Core Principle

The Economic Engine calculates the economic CONSEQUENCES of a proposed AI
scenario; it does not decide whether the organization should deploy it.

  Interviewer             -> facts
  Solution Estimator      -> technical scenario
  Economic Engine         -> economic consequences
  Decision Driver Analysis-> sensitivity and uncertainty
  Human                   -> final decision

9. SCORING SYSTEM

STATUS: implemented — calc/{economic_score,feasibility_score,risk_score,
composite,driver_ranking}.py; validated by scripts/scoring_cases.py;
weaknesses tracked in docs/scoring_system_todo.md

Scores are computed deterministically in calc/ from model outputs and inputs.
The LLM never outputs a numeric score; it only explains in plain language.

All scores EXPLAIN — they do not decide. Decision Drivers (9.5) are the primary
output; scores are supporting context (9.6).

Every score is computed twice: a headline value from input midpoints, and a
range from the input bounds. A score whose inputs are missing is reported as
NOT COMPUTABLE, never as zero and never with missing terms silently dropped.

9.1 Economic Score (0-100)

Based on payback period and benefit-to-cost ratio, grounded in the labor
baseline (spec 8.1), NOT in industry benchmarks — benchmarks cross-check the
baseline (8.8), they do not feed the score.

  Payback component:     piecewise-linear, <= 6 months -> 100,
                         >= 24 months -> 0, linear between
  Benefit/cost component: ratio of annual cost savings to first-year AI cost,
                         normalised so ratio 0 -> 0 and ratio >= 2 -> 100

Where no positive payback exists (8.7), the payback component is 0 — a
legitimate result, not an error.

9.2 Feasibility Score (0-100)

Three sub-factors, each normalised to 0-100 and weighted:

  data readiness           weight 0.45  user-reported, categorical
  automation achievability weight 0.30  estimator range
  integration complexity   weight 0.25  band (small/medium/large)

Data readiness carries the heaviest weight. Gartner predicts that through 2026
organizations will abandon 60% of AI projects that are not supported by
AI-ready data ("Lack of AI-Ready Data Puts AI Projects at Risk", press release,
26 Feb 2025, drawing on a Q3 2024 survey of 248 data management leaders in
which 63% did not have, or were unsure they had, adequate data management
practices for AI). Note this is a PREDICTION, not a measured outcome, and it
justifies weighting the factor heavily — it does not supply a number for the
score itself.

Data readiness must be captured as a CATEGORY, not free text: the LLM
classifies the user's description into a band (none / minimal / partial /
good / excellent) and deterministic code maps the band to a sub-score. This is
the same division of labour as the effort bands in 7.4 — the LLM interprets
language, code produces the number.

9.3 Risk Score (0-100, higher = safer)

Risk is probability x consequence, tracked as separate inputs:

  failure_probability  likelihood of a wrong/bad output (estimator range, or
                       derived from the selected architecture's error metrics)
  failure_impact       consequence severity, user-reported as a CATEGORY
                       (negligible / minor / moderate / major / severe)
  reliability_gap      required accuracy minus expected achievable accuracy;
                       adds risk only when positive
  compliance_exposure  a hard flag, not a numeric term

  raw_risk   = failure_probability x impact_weight  (both normalised 0-1)
  raw_risk   = raw_risk + reliability_gap penalty, capped at 1.0
  Risk Score = 100 x (1 - raw_risk)

Probability x impact is the conventional risk formulation (PMBOK / ISO 31000
lineage) and needs no vendor citation.

COMPLIANCE IS NOT A NUMERIC TERM. Where compliance constraints exist and the
selected solution does not cover them, the Risk Score is forced to 0 AND an
explicit blocker flag is raised. The flag surfaces regardless of what the
numeric score says — a compliance blocker must never be averaged away by
strong economics.

9.4 Composite Readiness Score

Weighted average of the three scores:

  Economic 0.40, Feasibility 0.30, Risk 0.30

Shown for context ONLY, and only when all three are computable — a composite
built from a partial set would imply completeness the assessment does not
have. It is explicitly labelled a summary indicator, not a decision mechanism.

9.5 Decision Drivers (replaces any recommendation/verdict)

The system does NOT output a category. It outputs a ranked list of the facts
that matter most to this specific decision, plus an explicit uncertainty
callout.

Ranking is a calculation, not a judgement call:

  sensitivity index (elasticity) = (% change in outcome) / (% change in input)

Each candidate variable is swept through its own plausible bounds, the affected
scores are recalculated deterministically, and elasticity is computed against
each. Variables with the largest elasticities are the drivers. Using
elasticity rather than raw swing matters: dividing by the input change makes
variables with different natural units and different sweep widths comparable.

The top drivers are rendered as factual statements produced by code — value,
range and provenance included — for example:

  "Labor is 72% of current process cost."
  "Expected automation is 55-70%."
  "Integration complexity: Medium."
  "Data readiness: Good."
  "Payback is 12-18 months."

The LLM phrases these in plain language. It does not choose which facts appear,
and it does not restate the numbers.

Uncertainty callout: the single input with the highest

  uncertainty index = relative range width x elasticity

i.e. a variable that is both influential and poorly known. A wide range on a
variable nothing depends on is not the biggest uncertainty, and neither is a
precisely known variable that dominates the outcome.

9.6 Presentation

- Every LLM-estimated value is shown as a range plus a confidence label, never
  a point (7.3, 9.6).
- Economic / Feasibility / Risk / Composite render on the Analysis screen as
  supporting context; the report LEADS with Decision Drivers.
- Outputs cite the benchmark or evidence behind any normalisation choice.
- A not-computable score is displayed as not computable, with the missing
  inputs named.

9.7 Overall Assessment Confidence

A top-level rating driven by how many fields are user_provided/sourced versus
estimated/assumed, and how wide the estimate ranges are. Interview quality
signals (a field the user contradicted, or that stayed low-confidence after
repeated attempts) feed this directly.

9.8 What the scoring system explicitly does NOT do

No recommendation label. No implicit lean framed as neutral fact ("this is
probably a PILOT situation" is exactly the sentence to avoid). No verdict
derived from crossing a score threshold. The system stops at ranked drivers
plus the biggest uncertainty, and hands the decision to a human.

10. AI INTERVIEWER

STATUS: implemented — interviewer/engine.py, interviewer/fields.py,
api/interview.py; voice variant in interviewer/voice.py + api/voice.py

Not a form. A short, adaptive, natural-sounding conversation that fills the
structured state with the minimum number of decision-relevant facts,
prioritised by decision relevance, while feeling like it is actually
listening.

10.0 Four-state machine
Stateless turn handler — no server-side session memory; the client ships the
AssessmentState back each turn.

    INTERVIEWING  -> need more information (ask a NEW field)
    CLARIFYING    -> existing answer is ambiguous/insufficient (re-ask/deepen)
    READY         -> minimum sufficient state reached (stop)
    UNCERTAIN     -> cannot obtain reliable info after reasonable attempts

Deterministic logic controls what is required, which need to pursue next, and
when the interview terminates. The LLM only interprets the latest response and
phrases the question — it never decides what to ask or when to stop.

10.1 State-driven, not history-driven
The next step is generated from the current structured state plus the most
recent user message only, not by re-reading the transcript. This keeps
latency and cost down and avoids drift.

10.2 Unresolved needs
A need may be: missing, ambiguous, low_confidence, contradiction, or
drill_deeper. The extraction step flags each extracted value with these
quality signals; the deterministic need-selector turns them into a ranked set.

10.3 Need selection (deterministic)
Each turn the engine scores every unresolved need as

  score = decision_priority(field) + severity_bonus(need_type) + required_bonus

and pursues the single highest. Severity ordering (highest first):
contradiction > ambiguous > low_confidence > drill_deeper > missing.

Relevance is enforced structurally: fields marked analysis_relevant=False are
never chased, and fields satisfiable by the benchmark pack
(benchmark_substitutable=True) are never asked for.

10.4 Realism techniques
- Never re-ask a field the user already stated, even implicitly
- Fill several fields from one answer when the user volunteers several facts
  ("about 10k tickets a month, handled by 15 agents" fills monthly_volume and
  current_headcount). The scored categories in section 5 rely on this: they
  are normally classified from the answer given to the free-text question, so
  they do not each cost an extra turn.
- Acknowledge before asking
- Vary phrasing — never reuse the field name as a template
- For a CLARIFYING need, ask ONE targeted follow-up referencing the existing
  value, not the same broad question again
- One question at a time, never two bundled in one message

10.5 Over-asking guard
Fields that do not feed the downstream analysis, or that a benchmark default
can satisfy, never cost a question. Never ask for information that is
irrelevant to the eventual analysis simply because it exists in the schema.

10.6 Termination
- READY: every required, analysis-relevant, non-benchmark field is resolved.
- UNCERTAIN: a field could not be resolved after MAX_ATTEMPTS (default 3), or
  the global question cap (default 12) is reached. What remains uncertain is
  reported explicitly and carries through to Overall Assessment Confidence
  (9.7) rather than being silently ignored.

`attempts` counts how many times the interviewer ASKED about a field — not how
many times extraction touched it. A fact the user volunteers unprompted must
never burn an attempt.

10.7 Model output contract
Every interviewer LLM call returns structured JSON: updated fields with values,
provenance tags and quality flags (ambiguous / low_confidence / contradiction /
needs_detail), plus the next question. This prevents the LLM from silently
calculating or inventing numbers inside a chat bubble.

10.8 Value never overwritten by an absence
An extraction result with a null or empty value never overwrites a value
already collected. "Not mentioned in this message" is not the same as
"the user retracted it".

11. ALTERNATIVES

STATUS: implemented — solution/alternatives.py, types in solution/schema.py;
validated by scripts/alternatives_cases.py

Up to 3 qualitative alternatives, compared against the primary proposal. No
separate economic model per alternative in the MVP.

What was actually built differs from the original wording in one important
way: the LLM does not GENERATE the alternatives. The candidate list is built
from the Solution Registry by deterministic code before any model is called,
and the LLM is handed that fixed list to explain. An id it invents matches
nothing and is discarded. The original phrasing ("LLM generates 2-3
alternatives") would have let the model introduce an architecture the registry
never vetted, which is the same regression 7.5 forbids for the primary
selection.

  Registry   the ONLY source of an architecture, provider, capability or
             benchmark figure in this section.
  Code       filters, decides materiality, and derives every band and metric
             using the SAME functions that produced the primary estimate
             (ranking.score_candidate, scope.effort_scope,
             performance.metrics_for, risks.controls_for) — an alternative is
             never evaluated by a parallel rule set.
  LLM        explains, in prose that passes a guard which drops any sentence
             containing a digit and any sentence carrying directive language.

Materiality is required: a vendor swap inside the same pattern and the same
implementation kind is NOT an alternative, because presenting it as one pads
the section without offering a real choice. The three difference kinds are
different_architecture, same_architecture_different_implementation_model, and
no_ai_baseline (the user's current process).

3 is a CEILING, never a target. Nothing is invented to reach it: if fewer
than two credible alternatives survive, fewer are shown; if none do, the
section says so, and every rejected candidate is recorded with its reason so
the absence is auditable. Categories the curated registry cannot supply are
named explicitly, so a gap reads as a registry gap rather than as a finding
that the approach does not apply.

`AlternativesResult` carries `is_recommendation = False` and
`economics_included = False` as constants, so a downstream presentation layer
cannot reframe the section as advice or as a costed comparison. Display order
reuses the primary ranker's own score; no second recommendation score is
calculated and the order is not a ranking of preference.

Surfacing alternatives is a fact, not a nudge (9.8): "what else could work" is
useful information and does not constitute a recommendation.

12. SENSITIVITY ANALYSIS

STATUS: implemented, but NOT in the shape originally specified.

Original wording: a threshold sweep in the form "the assessment would change
if automation rate > 72%". What was actually built is:

  8.10  deterministic recalculation of any exposed variable at its bounds
  9.5   elasticity ranking over those recalculations, plus the uncertainty
        callout

Elasticity answers "which variable moves the outcome most", which is what
Decision Drivers need. It does NOT answer "at what value does the picture
change", which is what a threshold sweep gives. The threshold form is still
worth having — it is more legible to a reader than an elasticity — and remains
open. It must not be phrased as a decision boundary ("decision changes if...")
because the system does not produce a decision to change; the honest phrasing
is which SCORE or FIGURE crosses which value.

DECIDED for the MVP report (13): DEFERRED. The final report renders the
existing recalculation and elasticity outputs only. A threshold form would be
new deterministic calculation, and the report layer is not permitted to
calculate. If it is built later it belongs in calc/, not in the report, and it
must refuse to report a crossing that falls outside the variable's own
declared bounds, that is non-monotonic across them, or whose metric is
undefined at either bound.

13. FINAL REPORT

STATUS: NOT BUILT — design approved, see
docs/deployIQ_final_report_proposed_fix.md

The report is a COMPOSITION AND PRESENTATION layer. It is not another
analytical engine. It consumes what the pipeline already produced and explains
it coherently.

13.1 What it consumes

  AssessmentState        the facts, with provenance per field
  SolutionEstimate       architecture, automation, effort, reference comparison
  EconomicResult         costs, savings, payback, absent components, warnings
  ScoreBundle            economic / feasibility / risk / composite + confidence
  DecisionDrivers        ranked drivers + the uncertainty callout
  AlternativesResult     registry-derived alternatives, already filtered
  SensitivityReport      recalculation at each variable's own bounds

These arrive as ONE frozen bundle from the orchestration layer. The report
never runs an engine itself. It must not recalculate economics or scores,
re-rank drivers, select architectures or alternatives, invent benchmarks,
costs or effort, turn assumptions into facts, turn scores into
recommendations, or let the LLM reinterpret a numerical result.

13.2 Structure — three layers, fourteen sections

The fourteen sections are unchanged. They are grouped by audience, because the
original flat ordering put an AI operating-cost breakdown ahead of the biggest
uncertainty for a business reader.

  Layer 1 — Decision
     1 Executive Summary        (framing only)
       Decision Drivers          <- the first substantive content
    14 What to Validate Next
       Assessment confidence, and what the analysis could not establish

  Layer 2 — Analysis
     2 Problem Definition        3 Current Process       4 Current Cost
     5 Proposed AI Solution      7 Implementation Reqs   8 AI Operating Cost
     9 Expected Benefits        10 Risks and Reliability
     6 Alternative Solutions    13 Sensitivity Analysis
       Economic / Feasibility / Risk / Composite, as indicators

  Layer 3 — Audit appendix
    11 Assumptions             12 External Sources
       Manifest, figure ledger, guard log, rejected alternatives, warnings

This resolves the ordering the earlier draft left contradictory: the Executive
Summary keeps position 1 as a frame, and Decision Drivers are the first
substantive content, immediately after it.

13.3 Provenance

Every material figure is visibly tagged. This is the core trust mechanism, not
optional styling. Every number traces back to a calc module, a registry entry
or a benchmark pack figure, never to LLM free text.

The five tags of section 6 are the only vocabulary. `verification` (4.3)
remains a SEPARATE axis and never becomes a sixth tag.

Interval arithmetic (calc/models.py) produces a DERIVED value that does not
carry the evidence ids of its inputs. The report therefore builds an EVIDENCE
INDEX: it walks the leaf values of the consumed objects, collects the
`source_id` present on each, and has a derived figure cite its INPUT SET
rather than a single id. A derived figure carries its provenance mix, its
contributing source ids, its derivation text and its originating module. This
is a report-layer index; the frozen calc layer is not modified to propagate
ids.

Where provenance cannot be established the report renders `provenance
unknown` and files a gap. It never guesses.

13.4 Absence is a typed state

Three states, three renderings, never collapsed:

  KNOWN           a value, with its range semantics
  ABSENT          never collected — excluded from the total, reason given
  NOT_COMPUTABLE  inputs missing — the missing inputs named

An ABSENT figure never renders as 0, blank, "none" or "no cost". A total with
absent components identifies itself as a floor, using the upstream
completeness note. A range is labelled as an envelope/bounds, not a confidence
interval, because interval arithmetic assumes the inputs move together. A
range is never silently collapsed to a point.

The report must carry what the analysis could NOT do: absent cost components
(8.2), unevaluated reference conditions (7.7), not-computable scores (9),
figures whose verification tier is below primary (4.3), unresolved interview
fields (10.6), registry coverage gaps (11), and an unresolved currency.

13.5 Executive Summary

The highest-risk section, because it can turn analytical facts into an
implicit recommendation. It is slot-filled, not free-form:

  1 what was assessed              5 labor realization policy
  2 what the analysis produced     6 assessment confidence
  3 what matters most (drivers)    7 biggest uncertainty
  4 modelled economics             8 constraints and blockers

It contains no score value and NO Composite Readiness Score — a composite in
a summary position becomes a verdict no matter what caveat sits under it. The
composite appears in Layer 2 only, with its caveats.

The engine's own payback statement and realization statement are used
verbatim rather than rephrased. These qualifiers are mandatory: cost savings
only; first-year view; not ROI; not a multi-year business case; confidence
describes how well-grounded the analysis is, not whether the opportunity is
good.

Banned throughout: recommended, best, viable, opportunity, worth it, should,
proven, will deliver, will reduce, ROI, go/no-go, justified, compelling.

13.6 Report modes

The pipeline has terminal states in which no primary solution or no economics
exists. The report has a shape for each, and never fabricates the missing
half:

  full      everything computed
  partial   economics or scores unavailable; the affected sections are present
            and explicitly empty
  refused   the estimator refused, or a compliance gap means no architecture
            was selected. No proposed-solution section and no benefits
            section is rendered at all.

13.7 Deterministic first, LLM optional

The deterministic half is complete on its own. With the LLM entirely
unavailable the report must still be valid, complete, numerically identical,
provenance-complete, absence-safe and non-recommending. The LLM is a
readability enhancement, never a source of fact.

It may only rephrase constrained, code-authored fragments. It never receives a
numeric figure: figures are injected by the deterministic renderer afterwards,
so a model that never saw a number cannot restate one wrongly. It may not
generate numbers, costs, percentages, scores, payback or economic conclusions;
select architectures or alternatives; rank drivers; invent or infer missing
data; turn assumptions into facts; recommend; or change the section structure.

Invalid model output is never silently repaired. The fragment falls back to
its deterministic text and the substitution is recorded.

13.8 Sensitivity in the report

The report renders the existing SensitivityReport. It shows each variable, its
OWN bounds, the metric at each bound, the swing, provenance, and the rows that
were skipped or could not be evaluated — those are not hidden. Direction is
never rendered as a bare "increases/decreases", because the direction
describes the metric, not the variable.

Sensitivity and Decision Drivers use deliberately different methods and are
not expected to agree on ordering. The report says so:

  Sensitivity      how far the metric moves at each variable's own bounds
  Decision Drivers which variables matter most, by elasticity against the
                   unbounded economic quantities

Threshold/crossing analysis (12) is NOT part of the MVP report.

13.9 What to Validate Next

Generated deterministically from upstream findings — the uncertainty callout,
high-impact estimated or assumed drivers, absent cost lines, missing score
inputs, unresolved interview fields, needs_more_information, unevaluated
reference conditions, divergent labor formulations, below-primary evidence, an
unavailable quality comparison, unknown compliance, and an unresolved labor
realization policy. Ranked by the driver impact already calculated; no new
scoring formula is introduced. Generic advice is never invented.

13.10 Validation

Report generation is FAIL-CLOSED. A report that violates a guardrail is not
emitted. At minimum: non-KNOWN figures carry no numeric value; KNOWN figures
carry provenance and derivation; money figures carry a currency or an explicit
currency gap; incomplete totals carry their completeness note; sourced
citations resolve in a registry; section ordering is deterministic; a refused
report contains no fabricated solution or benefit section; banned
recommendation language is rejected; LLM statements contain no digits; LLM
driver fragments preserve their qualifiers; the composite is absent from
Layer 1; an ABSENT value cannot be turned into a claim; required disclaimer
sentences are present; sanity flags stay visible; compliance blockers appear
in Layer 1.

13.11 Output

Markdown and JSON for the MVP. No HTML yet, and no PDF pipeline (18).

15. RESPONSIBILITY SPLIT

LLM — language only:
- understand the business problem, extract structured fields
- classify free text into the scored categories (5)
- phrase the next question
- decompose a workflow into capabilities; estimate per-task automation
- explain fit, write report prose and driver phrasing

Deterministic code — every number:
- validate state; compute labor, AI operating, implementation costs
- savings, first-year economics, payback, unit economics
- filter and rank solution patterns; select the implementation
- compute Economic / Feasibility / Risk / Composite scores
- rank Decision Drivers and select the uncertainty callout
- recalculate under sensitivity sweeps

Benchmark packs — external evidence:
static per-sector JSON with citations and verification tiers; compared
against calculated figures, never added to them (8.8).

There is no live research layer in the MVP; the packs are the whole of the
external-evidence surface.

16. TECH STACK

Backend: FastAPI (Python 3.12+), owns all LLM calls and all deterministic
calculation.
Validation/schema: Pydantic, single source-of-truth model (5).
LLM: OpenAI API, server-side only, never called from a client.
Calc: pure Python under calc/, no LLM and no framework.
Benchmarks: static JSON under data/sector_benchmarks/, loaded by
lib/benchmarks.py.
State: passed between client and server each request; nothing persists
server-side between requests.
Frontend/client: deferred.
No database. No auth. No queue. See ARCHITECTURE.txt for the module breakdown.
